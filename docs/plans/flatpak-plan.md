# Flatpak: the packaged application, and a shared runtime

**Status: phases 0 to 5 done, and phase 6 built except for its immediate
trigger.** Phase 0 (the spike) left the manifests in
[`flatpak/`](../../flatpak/), which build and run, and what it measured is
below. Phase 1 gave the project its `id`: `Application.Id`, the window class on
both backends, and the IDE asking for it when a project is created and editing
it afterwards. Phase 2 gave `Xml` namespaced attributes (`xml:lang`), phase 3
made `<id>.metainfo.xml` part of the project with its own editor, phase 4 built
the generator (`lib/package` + `tools/pack`), and phase 5 split the manifests
and added `tools/flatpak-build.sh`. Phase 6 is the test repository, and it
**exists**: `getbintana/flatpak` publishes the BaseApp, the IDE, the example and
an application from another repository, runs the smoke test before every
publish, and the issue this plan answered (`ISSUE-packaging.md`) is deleted.
What is left of it is at the end of its section. This plan is the design; what
the runtime can do is in [`llm/`](https://github.com/getbintana/bintana-llm/blob/main/docs/llm/README.md).

## What the application needed

To hand over a Bintana application -- and the IDE itself -- as something that
is installed and updated with `flatpak`, depending on neither the distribution
nor Flathub. The repository is **our own**, for a concrete reason: Flathub is
rejecting applications generated by AI, so distribution cannot go through it.

Two things follow, and this plan keeps them apart: **the shared runtime** (a
BaseApp that, once built, serves every Bintana application) and **the tool that
packages** a project, because whoever writes an application should not have to
write a manifest, a `.desktop` or a `metainfo.xml` by hand.

## What the spike measured

All of this was measured on this machine (GNOME 50, GTK 4.22.4, flatpak 1.18.2):

- **The installed layout already is the Flatpak layout.** The runtime resolves
  `share/bintana/{lib,ide}`, the reference and the examples by hops relative to
  its own binary, so `/app/bin/bintana` finds `/app/share/...` with **no change
  to the C**.
- **Build times**: BaseApp 43 s (QuickJS and the whole runtime), IDE 2 s,
  example 2 s.
- **The GNOME SDK carries** GTK 4.22.4, GtkSourceView 5, sqlite 3.50.4, libsoup
  3.6.6, GStreamer 1.26.11 **with `libgstgtk4.so`** (`Video`'s sink),
  gtk4-unix-print, libxml2 2.14.6 and libsystemd 261. **It has no VTE** (which
  is why `Widget.Available("Terminal")` is `false`: 46 of 47 types), no git and
  no compiler.
- **The journal works inside the sandbox** (`Logger.Target = "Journal"` reached
  the host's journal).
- **The BaseApp is a build dependency, not a runtime one**: it was uninstalled
  and the IDE kept running; its files are copied into each application's commit
  and the disk deduplicates them. The IDE is **2.5 KB** of new content over the
  BaseApp.
- **What follows from that**: updating the BaseApp does **not** update the
  applications; they have to be rebuilt and republished.
- **A static repository is enough**: served with `python3 -m http.server`,
  `remote-add` + `install` + run, with no other tool.
- **flatpak 1.18.2 has bug [#6818](https://github.com/flatpak/flatpak/issues/6818)**
  (`build-init --base` fails with `lsetxattr(security.selinux)`), fixed in
  1.18.3. It is not SELinux: it fails the same way in Permissive mode. CI
  (Ubuntu 24.04, flatpak 1.14) does not hit it.

## Decisions

- **`project.btp` declares `id`** (reverse DNS). The runtime validates it with
  `g_application_id_is_valid` and refuses the project with a sentence if it is
  not valid.
- **`Application.Id` is published** and used as the `GtkApplication`'s
  `application_id`; the runtime also calls `g_set_prgname(id)`, because X11
  builds `WM_CLASS` from the program name and ignores the application id
  (Wayland does not: `gdktoplevel-wayland.c`). With that, `StartupWMClass` is
  the id on both.
- **`<id>.metainfo.xml` is editable**, with `<id>` and `<name>` validated
  against `project.btp`.
- **The generator is `lib/package` + `tools/pack`**, not a runtime verb.
- **The ids are `io.github.getbintana.*`** until the official publication; the
  community repository (`flatpak.getbintana.org`) can change them before that.
- **The BaseApp carries neither the IDE nor the examples.** If it did, any
  change to `ide/` would change the BaseApp and force everything to be rebuilt;
  split, a change to one application rebuilds that application.

## Phase 1 — Identity

`project.btp` gains `id`. The runtime reads it in `bta_app_new`, validates it
and publishes it as `Application.Id`; `bta_app_run` creates the
`GtkApplication` with that id (and with none, as before, when there is none).
The IDE asks for it when a project is created, edits it in `ProjectForm` and
uses it for the menu entry `Apps.js` writes. The IDE's `.desktop` files move to
`StartupWMClass=io.github.getbintana.Ide`, and the comment on the `exec -a` in
`tools/bintana-ide.in` is updated: with an id, the runtime sets the class.
`ide/project.btp` and `examples/hello/project.btp` declare their own.

## Phase 2 — Namespaced attributes in `Xml`

`Xml.SetAttrNS(uri, name, value)`, `AttrNS(uri, name)` and `RemoveAttrNS`.
`SetAttr` refuses `:` on purpose, so `xml:lang` could not be written, and that
is exactly what AppStream needs for translations. It is C in `bta_xml.c`, and
the rest of the DOM does not change.

## Phase 3 — The metainfo as part of the project

`<id>.metainfo.xml` at the root of the project. The IDE opens it as highlighted
text (`EDITABLE.xml`) and in a structured form (`MetainfoForm`, after the
`PoForm` pattern): it reads with `File.LoadXml`, edits the common fields -- id,
name, summary, description with languages, developer, licences, URLs,
categories, releases, launchable -- and saves with `File.SaveXml`, **keeping
what it does not edit** (the DOM keeps unknown elements and attributes). It
checks that the `<id>` and the `<name>` with no language match `project.btp`.

## Phase 4 — The generator

`Desktop.Entries.Write(path, entry)` in the runtime -- the verb by path the
module lacked, reusing `Install`'s body -- and `lib/package` with a `Package`
class that writes, for a project:

- the validated metainfo,
- `<id>.desktop` through `Desktop.Entries.Write` (`Exec`, `Icon`,
  `StartupWMClass`),
- the Flatpak manifest **as JSON** (flatpak-builder accepts it, so no YAML
  writer is needed),
- the icon, by convention `icons/<id>.svg`.

`tools/pack` is a console project (no display) with its `.sh`, for CI and for
use by hand. `appstreamcli validate` and `desktop-file-validate` check the
output.

## Phase 5 — Building

`tools/flatpak-build.sh` builds the BaseApp and the applications, runs
`flatpak build-update-repo --generate-static-deltas` and leaves the repository
staged. The manifests are split the way the decisions say: the BaseApp keeps
the runtime and the libraries, and the IDE and each example carry their own.
An optional `Dockerfile` builds locally without touching the host (bwrap needs
`--privileged` or `/dev/fuse`).

## Phase 6 — The test repository and its CI

The repository exists (`getbintana/flatpak`), with the workflow and a
`gh-pages` branch that publishes; the manifests stay in the main repository so
they are not duplicated. CI builds the BaseApp, the IDE, the example and an
**application from another repository** (which is what exercises a third
party's whole road), publishes with `--generate-static-deltas` and no
signature, and **runs the smoke test before the push**: the runtime's
`--version` inside each package plus a console project through each one, which
is what catches a package that builds and does not run.

**What is incremental is recorded, not guessed**, and the rule lives where it
cannot go stale: `builds.json` in the published repository keeps, per ref, the
commit built, its source repository and the hash of its input, and
[`flatpak/ci/README.md`](../../flatpak/ci/README.md) has the table of what
rebuilds what, including the case no commit of any source can show (a
`finish-args` that changed).

**What is left of this phase is the immediate trigger**: today a new tag waits
for the `schedule` or a manual `workflow_dispatch`, and a `repository_dispatch`
from the main repository's workflow needs a token. The SDK is cached
(`actions/cache` over `~/.local/share/flatpak`): it is 837 MB per run.

## What is deliberately not here

- **VTE in the BaseApp.** The IDE does not need it (its output panel is a
  `TextEditor`); `Terminal` stays a capability an application builds in if it
  wants it. If the community repository offers it, it is a module of the
  BaseApp and a decision for that phase.
- **git inside the IDE's sandbox.** It is not in the runtime; the ways out are
  packaging it, `flatpak-spawn --host` with `--talk-name=org.freedesktop.Flatpak`,
  or saying it is not there. It is a decision for the IDE, not for packaging.
- **`Desktop.Entries` inside the sandbox**, which writes to a private
  `XDG_DATA_HOME` and does not reach the host's menu. An `Exec` of
  `flatpak run <id>` is the likely fix, and it touches the runtime.
- **The community repository.** This plan provides the tools;
  `flatpak.getbintana.org` is a later infrastructure decision.

## Tests

- `tests/widgets`: `Application.Id` and the refusal of an invalid id; `Xml`'s
  NS verbs; `Desktop.Entries.Write`.
- `tests/ide`: creating a project asks for an id; `ProjectForm` edits it;
  `Apps` uses it; the metainfo editor opens, validates and saves.
- `tests/api.sh` kept current at every phase, as the rule requires.
- The test repository's CI runs the Flatpak smoke test; `tests/install.sh` is
  still the check for the ordinary install.
