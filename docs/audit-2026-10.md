# Audit, October 2026: the language, the runtime, the widgets and the IDE against the field

**Status: open, last checked 2026-11-11.** An independent audit, written on
2026-10-10 without taking the repository's own documents on trust: every claim
was checked against the code, and where it could be, against a probe. Each
finding has an id so the work can be picked up one at a time; when one is
answered it is **deleted**, as `docs/issues/` does -- the answer goes where the
reader looks, and this file keeps only what is still owed, and goes the same way
when the last one is.

How each finding was established, in the **Evidence** line:

- **probe** -- reproduced with a console project or on a virtual display
  (`tests/try.sh`), and the output is quoted;
- **code** -- read in the source, at the place named; not run;
- **claimed** -- a number the repository states and the audit did not re-measure.

The IDE half (section 4) was code reading only for this audit: the IDE was not
started. The suite drives it now.

Severity is **High** (blocks a class of application, or a silent wrong answer),
**Medium** (costs real work or surprises) and **Low**.

## 1. The language

### L2. Asynchrony is callbacks only -- High
- No `async`, no `Promise` (both by decision), no blocking `MsgBox` either. A
  sequence of I/O is nested callbacks or a `*Wait` that freezes the window
  (the wait now has a default timeout, but it still freezes it).
  `docs/plans/async-plan.md` is the open answer.
- **Field.** Gambas, VB6, Delphi and Xojo answer with blocking modal dialogs;
  .NET, Python and Electron with `await`. Bintana has neither.

### L8. Interpreter only -- Low/Medium
- Debug `fib(27)` ~64 ms (probe). Release numbers in `docs/testing.md` are
  claimed: on par with or ahead of CPython on floating point, up to 1.6x behind
  elsewhere. Enough for forms and CRUD, weak for bulk data on the UI thread.
  `docs/plans/interpreter-plan.md` is the open answer.

## 2. The runtime library

### R3. D-Bus and global hotkeys are missing -- Low/Medium
- **TCP, Unix, UDP, WebSocket, SMTP, serial, TLS and the tray are built**
  (`Socket`/`ServerSocket`/`UdpSocket`/`WebSocket`/`SmtpClient`/`SerialPort`,
  with line mode and parts; [transports-plan.md](plans/transports-plan.md),
  stages 1 to 6). A clicked notification reaches the program through
  `Notification.OnActivate` on Linux/macOS and through the Windows WinRT toast,
  buttons included. The tray is built on Linux (`StatusNotifierItem` +
  `dbusmenu`) and on Windows (`Shell_NotifyIcon`); macOS is a stub until its
  stage ([tray-plan.md](plans/tray-plan.md)).
- **Missing:** D-Bus, both as a client and as a service that answers on the
  session bus, and global hotkeys, which GTK4 has no API for.
- **Impact.** Linux desktop integration -- a service another program calls, a
  legacy daemon, a global shortcut for a tray application.
- **Field.** Gambas `gb.dbus`, Qt DBus, Electron's global shortcuts.

### R5. Windows without the windowed suite, macOS not started -- Medium
- The `windows` CI job builds, runs `tests/api.sh`, the project pass
  (`tests/check.sh`) and the smoke project on a real Windows 11 desktop; the
  rest of the windowed suite does not run there, and the portable zip is
  unverified until somebody opens it on a Windows desktop.
- The platform's pieces are built: `Terminal` (ConPTY + libvterm), `Exec`'s
  `Control` stream (a named pipe in `BINTANA_CONTROL_PIPE`, so the debugger
  works), `Keyring` (Credential Manager), `Printer.Names`/`Default`
  (`EnumPrintersW`/`GetDefaultPrinterW`), `SerialPort`, `Tray`, clickable
  notifications and the debugger.
- `docs/plans/macos-plan.md`: not started.

### R7. Deployment -- Medium
- Flatpak (via `lib/package`, command line), a tarball and an NSIS installer. No
  AppImage, deb or rpm; no signing; no updates. Sources ship in the clear
  (`docs/plans/bundle-plan.md` is a plan).

### R8. No encrypted database -- Low/Medium
- `Keyring` keeps secrets and `Cipher` seals a value; neither is a store. A
  business application that needs its database file encrypted has no answer
  beyond the engine's own (SQLCipher, or the server's encryption).
- The rest of the pieces are built: `Dialog.Font`, `Dialog.OpenFiles`, a
  question through `lib/dialog`'s `Confirm`, `Bitmap` (scale, crop, rotate),
  and PDF read, write, encrypt, sign and verify (`PdfDocument`, `Probe.Pdf`,
  `lib/pdfview`, `Printer.Preview`).

## 3. Widgets

### W3. Business controls missing -- Medium
- Tag input; rich text editing; a web view (no WebKitGTK); a
  status bar, docking, splash, wizard, accordion or scheduler as controls.
  In favour: `DecimalBox` is exact and locale-aware (probe: `1234.567` ->
  `1234.57`, text `1234,57`). A toolbar is a `Panel` with `Style: "toolbar"`,
  not a missing control. Masked input (`TextBox.Mask`), a completion list
  (`TextBox.Completion`, the editable combo), a property grid for
  applications (`lib/propertygrid`) and a PDF viewer (`lib/pdfview`) are built
  and are not part of this.

## 4. The IDE (code reading only)

### I2. `Exec` is the one non-visual object that is not a part -- Low
- `Timer`, `Connection`, `Model` and `HttpClient` are parts now: the `.form` carries
  them in `components`, the designer has a tray, the tree lists them, the
  property grid edits their properties, and a form that closes stops them.
- **`Exec` is not a class and has no object to own.** It is a global with
  statics (`Exec.Run`, `Exec.Wait`), so a part would be a wrapper with no
  state or a different shape; nothing in the tree asks for one yet.
- **Direction.** A wrapper only if an application asks to configure a child
  process's environment in the designer; until then `Exec` stays the global it
  is.

### I10. Smaller gaps -- Low/Medium
- Git: no blame, stash, merge or conflict resolution, no amend or hunk staging;
  commit is a single `-m` (`ide/modules/Git.js`, ~574).
- No IDE extensibility; templates are *a form* or *a function*. *Project → Run
  with profiling* and the accessibility check are built.
- Undo keeps up to 200 JSON snapshots of the whole tree per edit; not measured
  on a large form.

## 5. Against the field

Versions as found on 2026-10-10; Bintana's own row was checked again on
2026-11-11. Prices for Qt, PureBasic and B4J's exact version could not be
confirmed in 2026 sources.

| | Bintana | Gambas 3.22 | Lazarus 4.8 / Delphi 13 | Xojo | Qt / .NET | Electron / Tauri |
|---|---|---|---|---|---|---|
| Platforms | Linux; Windows builds and passes the smoke suite, the rest of the windowed suite not run; macOS not started | Linux | All | All | All | All |
| Databases | SQLite, ODBC (SQL Server, MySQL, PostgreSQL, Firebird ...) | SQLite, MySQL, PostgreSQL, ODBC | Many | Several | Many | npm |
| Data binding | Yes (`Form.Record`, `Bind`, `Source`) | Yes | Yes | Partial | Yes | Frameworks |
| Report designer | Yes (`lib/report`, bands on a page) | Yes | Yes | Basic | Third party | npm |
| Accessibility | Yes (properties and the IDE's check) | Partial | Yes | Partial | Yes | Yes |
| Language | Curated JS with modules; no async | BASIC | Compiled Pascal | Own | C#/C++/Python | Full JS/TS |
| Licence | MIT, free | GPL | GPL/LGPL; Delphi commercial | 499-1999 USD/year | LGPL or commercial | MIT |

- **Gambas is the mirror**: same idea, same Linux niche, twenty years ahead.
  Bintana wins on a language half the world knows, MIT, GTK4, Flatpak,
  correctness and i18n; databases (ODBC) and networking (sockets, WebSocket,
  SMTP) are now covered, and it still loses on maturity and on the size of its
  ecosystem.
- **Lazarus and Delphi set the expectation** for a forms programmer:
  non-visual components, data-aware controls, banded reports.
- **Against Electron/Tauri** the argument is weight and nativeness; it wants
  published numbers (package size, memory).
- **GNOME's tools** (Cambalache 1.0, Workbench, Builder) are good designers with
  no data, reports or VB-style events: they make GNOME apps, not business
  systems. That gap is the niche.
- **Flutter desktop** is now maintained by Canonical: the modern competitor on
  Linux, with no visual designer and no RAD model.
- **Trust signals** a newcomer needs: a dated release and a changelog now exist
  (0.3.0); the Flatpak repository exists but is not Flathub; complete examples
  (clients, quote, bound, invoices) are there; a forum is still missing.
- **Documentation written for an LLM** is a differentiator no classic
  competitor has.

## 6. Order of attack

1. **R7 and R5**: AppImage, signing and updates; the windowed suite on Windows
   and macOS.
2. **L2**: a chain of waits is still nested callbacks; decide it with an
   application rather than on spec -- `Task` already makes work straight-line.
3. **R8, R3, W3 and I10**: an encrypted store, D-Bus, the business controls
   that are still missing, and the IDE's smaller gaps -- Git's merge and
   conflicts, extensibility, templates.

`Database.Postgres` is no longer a finding: `Database.Odbc` answers the class
of application the audit named, and the native libpq driver is the next
improvement in [`plans/postgres-plan.md`](plans/postgres-plan.md).

The database tools, the report designer, the editable combo, masked input,
explicit grid placement, right-to-left and *Arrange in boxes* were the rest of
this list, and are built.

What the audit found sound and worth keeping as it is: argument refusals
stricter than any competitor's; `Exec` with no implicit shell; XML with no
network or entities; zip refusing escaping names; TLS pinning with resumption
off; exact `Decimal` arithmetic; real threads with `Task`/`Lock`; `Record`
round-tripping JSON, XML (in sequence order) and SQLite; optional dependencies
degrading honestly; the API contract checked against the code; the debugger's
protocol; declarative i18n of prose.
